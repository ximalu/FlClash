AGENTS.md — FlClashTier 项目研发原则

1. 项目定位

FlClashTier 是一款面向真实用户的软件产品，而不是仅供开发者个人使用的网络实验工具。

开发目标不仅是实现技术功能，还包括：

- 普通用户能够顺利安装和使用；
- 网络环境变化时能够自动恢复；
- 不要求用户理解复杂的网络技术；
- 不依赖用户手动修改路由器、防火墙或系统配置；
- 在不同网络环境下具有稳定、可预测的表现。

2. 技术决策必须考虑产品属性

提出技术方案时，不能只考虑开发者当前的设备和网络环境。

必须区分：

- 开发环境：开发者自己的设备、网络和服务器；
- 测试环境：用于验证不同网络条件的环境；
- 用户环境：普通用户实际使用的软件环境。

某个方案在开发者自己的环境中可行，不代表它适合作为产品方案。

特别注意：不能把要求用户开放公网端口、修改路由器配置、手动维护连接等操作，默认视为合理的产品解决方案。

3. 优先解决根因，而不是掩盖症状

遇到连接延迟、网络切换、服务恢复等问题时：

1. 首先分析完整的技术链路。
2. 找出问题产生的具体机制和责任组件。
3. 区分协议限制、架构限制、实现缺陷和配置问题。
4. 优先寻找软件自动处理的方案。
5. 对无法消除的限制，明确说明原因和影响。

不能因为当前实现存在限制，就直接把该限制定义为产品应当接受的行为。

4. 技术方案评价标准

提出多个方案时，除了开发成本，还必须考虑：

- 用户使用门槛；
- 安全性；
- 可靠性；
- 不同网络环境下的兼容性；
- 故障恢复能力；
- 长期维护成本；
- 对现有架构的影响。

必须明确区分：

- 临时调试方案；
- 开发阶段的验证方案；
- 正式产品方案。

三者不能混为一谈。

5. Agent 的研发职责

Agent 不只是执行用户提出的修改指令，也需要承担研发分析职责。

如果发现用户提出的方案可能只是绕过问题，而不是解决问题，应当主动指出。

如果当前技术实现与产品目标存在冲突，应当优先报告这种冲突，而不是默认接受现状。

不得为了快速给出一个可执行答案，而省略必要的架构分析和技术验证。

6. 结论必须有证据

区分以下内容：

- 已经通过实验验证的事实；
- 根据现有证据作出的推论；
- 尚未验证的技术假设；
- 需要进一步测试的问题。

不得把推测包装成确定结论。

所有涉及产品行为的重大修改，都应尽可能通过实际测试验证。
